# Local Codebase Navigator

**非公開コードをローカルで解析し、変更に関連するファイルと根拠をエディター内で確認する。**

TypeScript / JavaScriptのコードを索引化し、検索条件に関連するファイル、依存関係、既存テストの候補を示すVS Code拡張です。結果から根拠のコード行へ移動できます。主要な検索はモデルなしで動き、任意でローカルOllamaによる文章化を利用できます。

| 項目 | 内容 |
| --- | --- |
| 開発形態 | Codexによる実装・検証・レビュー支援を活用した個人開発 |
| 現在の範囲 | ローカルで動作するVS Code拡張。検索と根拠確認を中心に、ローカルAIの評価も継続 |
| 技術 | TypeScript、Node.js、VS Code Webview、Tree-sitter、SQLite FTS、Ollama（任意） |
| 検証 | Vitest、Promptfooを含む合成評価、Extension Host試験、配布VSIX導入試験、GitHub Actions |

## 解決したい課題

既存コードを変更するとき、文字列検索で見つかったファイルだけでは、利用先や関連テストまで見渡せません。一方、非公開コードを外部AIへ送ることを前提とした調査は、扱うデータによって利用しにくい場合があります。

そこで、ローカルで得られる宣言・本文・依存の情報から候補を提示し、開発者が根拠を開いて判断できるようにしました。変更の自動実行や、影響範囲の完全な特定を目的とするものではありません。

## 合成サンプルでの操作例

画面キャプチャ・動画は後日追加予定です。以下は合成した小さな買い物処理のコードを使う操作例で、今回の記事作成時に撮影や再測定を行ったものではありません。

1. **調査を開始する。** パネルに `discount` と入力して検索します。エディターで選択した文字列やファイル、Git差分からも調査を始められます。
2. **候補と理由を確認する。** 割引処理が上位に表示され、利用側や関連テストを依存関係の根拠とともに確認できます。候補をパスなどで絞り込み、依存経路を図とリストでたどれます。
3. **根拠の行を開く。** 結果内の根拠からエディターの該当行へ移動します。候補が挙がった理由をコードで確かめ、変更対象を判断します。
4. **調査を止めてやり直す。** 実行中の処理を中止し、条件を変えて再検索します。中止・期限超過・失敗を、完成した結果として扱わない設計です。

この例が示すのは、用意したコードに対する操作と期待値です。実プロジェクトでの調査時間の短縮や、候補の網羅性を証明するものではありません。

## 構成と処理の流れ

| 段階 | 役割と受け渡すもの |
| --- | --- |
| VS Code / Webview | 検索条件・対象フォルダーを受け取り、進捗・候補・根拠を表示する |
| Workspace Extension Host | 設定と対象を確認し、Workerへ調査を依頼する。結果から実ファイルへの移動も扱う |
| Worker / Tree-sitter | 上限・除外条件の範囲でファイルを読み、宣言や依存の情報を抽出する |
| SQLite FTS / 候補選定 | 本文検索と宣言・パス・依存の情報を組み合わせ、理由を追える候補を作る |
| 任意のOllama文章化 | 選定済みの根拠を入力予算内で渡し、応答形式・引用を検証する。問題があれば理由付きで既定の結果へ戻る |
| 任意の保存 | 永続索引・履歴はそれぞれ明示的に有効化する。保存内容・期限・削除手段を定める |

主要な検索経路はOllamaへの接続を必要としません。文章化を有効にした場合も接続先はloopbackに限定し、クラウド無効の確認を要求します。Remote環境ではlocalhostが開発者のPCではなく、拡張が動く接続先を指す点も表示します。

## 設計で重視したこと

### 候補の順位と根拠を説明できるようにする

宣言・パス・本文への一致と依存関係を組み合わせ、候補には順位の内訳と根拠を付けます。スコアは正解の確率ではありません。全文検索に加えて構造の情報を使うことで、同じ語を含むコメントと、実際の利用関係を区別して検討できます。

関連テストも、命名上の対応と直接・間接依存の根拠を区別します。動的な呼び出しや解決できない依存もあるため、出なかったファイルが無関係とは断定しません。

### エディターの応答性と処理の終了を両立する

解析をWorkerへ分離し、入力の上限、期限、中止と復帰を扱います。長い処理を画面側から切り離しても、停止したWorkerが残ったり、古い結果が返ったりすれば、次の調査を安心して始められません。

複数OSの検証では、子プロセスの終了通知とIPC経由の結果受信が競合する問題が見つかりました。OS側の終了だけで受信完了と判断せず、通信の終了を踏まえて結果と終了待ちを扱うよう修正しました。正常系の検索だけでなく、中止後の再調査や終了時の挙動も検証対象にしています。

### 保存・外部送信を利用者が選べるようにする

永続索引と調査履歴は既定で無効です。保存する場合はコード本文や問い合わせが残ることを説明し、保持期限や削除手段を用意します。ローカル保存でも、何をどこに残すかという判断は必要です。

任意のローカルLangfuse計測は、処理名・時間・件数・状態などのメタデータに用途を限定します。検索に必要な処理、文章化、保存、観測を別々に選べる構成にしています。

### AIの形式合格と、説明の有用性を分ける

既存のローカルモデルと合成ケースを用い、入力の長さ、応答時間、引用、同時要求などを比較しました。応答形式が合格しても、引用が説明を十分に裏付けない場合があります。速度が改善しても別のケースで品質が落ちる変更は、既定として採用しない判断を記録しています。

現時点ではモデルの既定採用を保留しています。人手による回答品質の評価や実プロジェクトでの有用性確認は、自動テストとは別の残課題です。

## 学びと担当範囲

- **根拠を開けることが、候補の採否を判断する入口になる。** 順位だけでなく、宣言・依存・本文のどの情報から候補になったかを確認できる設計にしました。
- **中止は画面表示を止めるだけでは完了しない。** Workerの終了、結果の受信、次の調査への復帰を一緒に扱う必要がありました。
- **ローカル実行にも境界がある。** 保存の選択、処理ホスト、loopbackの接続先を明示することが必要でした。
- **AIの採用判断には自動評価だけでは足りない。** 形式、引用の対応、意味的な品質、応答性を分けて記録することが重要でした。
